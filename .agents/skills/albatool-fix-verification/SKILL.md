# Albatool Fix Verification — لا تعديلَ بلا عطلٍ مُثبَت

القاعدة الواحدة: **كل تعديل يجب أن يُشير إلى سطرٍ يُنتج العطل، وإلى فحصٍ كان
يسقط قبله وينجح بعده.** التعديل الذي لا يُقابله عطلٌ مُعاد إنتاجه ليس إصلاحاً
بل تخميناً — وقد يخفي العطل الحقيقي فيعود بعد أسبوع.

## متى تُطبَّق

- بلاغُ عطل بأي صيغة: «فيه مشكلة»، «الزرّ ما بيشتغل»، «الرقم غلط».
- قبل أي كوميت يُقدَّم على أنه إصلاح.
- **خصوصاً** حين يقول المستخدم إن عطلاً أُصلح سابقاً ما زال قائماً — فهذا
  دليلٌ على أن الإصلاح السابق عالج عَرَضاً لا سبباً، أو عالج موضعاً واحداً من
  عدّة مواضع.

## البروتوكول — خمس خطوات لا تُختصر

### 1) حوّل الشكوى إلى جملةٍ فيها رقم

«يظهر رقم بكسور» لا يكفي. اسأل الكود حتى تصل إلى:
«فتح فاتورة قديمة ← إضافة صنف ← يظهر 763.63 بدل 51,800».

بلا مثالٍ برقمَين — الخطأ والصواب — لا سبيل للتحقّق لاحقاً.

### 2) اعثر على السطر، لا على الملف

اقرأ المسار كاملاً من الحدث إلى الرقم المعروض. المواضع التي تكذب كثيراً:

| العَرَض | ابدأ من |
|---|---|
| رقمٌ خاطئ في جدول البنود | دوالّ `pickProduct*` ثم `updateRow` ثم مسار الحفظ |
| زرٌّ «لا يعمل» بلا رسالة | ردّ Supabase: `error === null` **مع صفر صفوف** — سياسة RLS تمنع بلا خطأ |
| صفوفٌ ناقصة في شاشة إدارة | حدّ 1000 صف الافتراضي — استعلامٌ بلا `range` |
| رقمٌ يختلف بين شاشتين | حسابٌ مكرَّرٌ في موضعين بدل مصدر واحد |

### 3) اكتب الفحص الساقط **قبل** الإصلاح

الفحص الذي لا يسقط قبل الإصلاح لا يحرس شيئاً. شغّله وتأكّد أنه أحمر:

```bash
npx vitest run src/test/<الملف>.test.ts
```

### 4) أصلح السبب — وابحث عن توائمه

العطل في Albatool يتكرّر لأن الحساب مكتوبٌ في مواضع متفرّقة. بعد إيجاد
الموضع، ابحث عن نمطه في المشروع كلّه قبل الإصلاح:

```bash
rg 'fp \* r\.exchange_rate' src        # نفس الحساب في شاشة أخرى؟
rg '\.delete\(\)\.eq\("id"' src        # نفس مسار الحذف بلا تحقّق؟
```

أصلحها كلّها في الدفعة نفسها، وأضف **فحصاً بنيوياً** يمنع عودة النمط:

```ts
it.each(ENTRY_SCREENS)("%s: لا ضربَ مباشراً في المعدّل", (file) => {
  expect(read(file)).not.toMatch(/unit_price:\s*\w+\s*\*\s*\w+\.exchange_rate/);
});
```

### 5) تحقّق بالثلاثة، ثم صف العطل في الكوميت

```bash
npx vitest run
npx tsc -p tsconfig.app.json --noEmit
npm run build
```

ورسالة الكوميت تصف **العطل** لا التغيير: ما كان يحدث، ولماذا، وما الذي يمنع
عودته. «أصلحت المعدّل» لا تفيد قارئها بعد ستة أشهر.

## علامات أن «الإصلاح» ليس إصلاحاً

- لا فحصَ يسقط قبله.
- يضيف شرطاً على العرض بينما الخطأ في الحساب المخزَّن.
- يعالج موضعاً واحداً ونمطُه موجودٌ في ثلاثة.
- يبتلع خطأً (`try/catch` فارغ) بدل معالجته.
- «صار يشتغل» بلا تفسير لسبب توقّفه.

## الفخّ الخاصّ بهذا المشروع: النجاح الكاذب

`supabase.delete()` و`update()` **ينجحان بصفر صفوف** حين تمنع سياسة RLS
الصفَّ — بلا خطأ. فرسالة النجاح تظهر، والصفّ يختفي تفاؤلياً، ثم يعود عند أوّل
تحديث. أي مسارٍ يكتب أو يحذف يجب أن يطلب المتأثّر ويتحقّق منه:

```ts
const { data, error } = await supabase.from(t).delete().eq("id", id).select("id");
if (error) throw error;
if (Array.isArray(data) && data.length === 0) throw new Error("لم يُحذف السجل — تحقّق من صلاحيتك");
```
